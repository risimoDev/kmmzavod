# /full-audit — оркестрация (выполняет основная сессия Opus)

Ты — оркестратор. Субагенты делают объёмную работу, ты думаешь: строишь план, проверяешь находки, распределяешь задачи, берёшь на себя сложные и вычищаешь ложные срабатывания. Ничего не принимай на веру из отчёта субагента без проверки ключевых находок по коду.

Аргументы: `$ARGUMENTS`
- область: `all` (по умолчанию) или ключи из таблицы областей ниже через запятую (`api,web`).
- `--audit-only` — только аудит и план, без правок.
- `--auto-features` — реализовать одобренные тобой новые функции/доработки без отдельного подтверждения пользователя (по умолчанию — спросить).

## Команда
| Агент | Модель | Для чего |
|---|---|---|
| `scout` | Haiku | typecheck, тесты, py_compile, prisma validate, audit зависимостей, health, инвентарь, сжатие логов |
| `quick-fixer` | Haiku | механические правки ≤30 строк в 1 файле без решений по логике |
| `code-auditor` | Sonnet | аудит корректности/контрактов/производительности; режим `diff` — ревью правок |
| `security-auditor` | Sonnet | аудит безопасности области |
| `e2e-tester` | Sonnet | живые сценарии на localhost |
| `implementer` | Sonnet | фиксы, оптимизации, доработки, новые функции по брифу |
| ты (Opus) | Opus | план, триаж, сверхсложные задачи, финальные решения |

Вызывай через Agent с `subagent_type: "<имя>"`. Независимые вызовы — в одном сообщении (параллельно), не более ~8 одновременно.

## Области
| Ключ | Пути | Акценты |
|---|---|---|
| api | apps/api/src (routes, plugins, lib) | authz, tenant-изоляция, zod-валидация, rate-limit |
| admin | apps/api/src/routes/admin*, apps/web/src/app/(app)/admin | доступ только admin |
| orchestrator | apps/orchestrator/src | воркеры BullMQ: идемпотентность, повторы, зависшие статусы, автопилот |
| web | apps/web/src | контракт с api.ts, ошибки/пустые состояния, XSS, производительность |
| db | packages/db/prisma, packages/queue, packages/storage | индексы, связи, каскады, миграции, presigned URL |
| ai | packages/ai | обработка ошибок внешних API, таймауты, стоимость вызовов |
| media | apps/editor, apps/video-processor | ffmpeg/subprocess-инъекции, SSRF при скачивании, утечки temp-файлов, память |
| publisher | apps/publisher | хранение сессий/кук соцсетей, SSRF, ретраи |
| farm | apps/device-agent | только статический анализ (ферма на другом ПК!) |
| infra | docker-compose*.yml, infra/, scripts/, Dockerfile-ы | открытые порты, root, секреты, nginx-заголовки, TLS |

## Фаза 0 — подготовка (ты сам)
1. `git status --short`, `git log -5 --oneline`. Если есть незакоммиченные изменения — спроси пользователя (AskUserQuestion): закоммитить их сначала / работать поверх / только аудит. Никогда не откатывай и не стэшь чужие изменения.
2. Создай папку отчёта `docs/audit/<YYYY-MM-DD>/`. Туда пишешь только ты: `BASELINE.md`, `FINDINGS.md`, `PLAN.md`, `REPORT.md`.
3. Заведи план задач в update_plan по фазам.

## Фаза 1 — baseline (параллельно, scout)
Одним сообщением запусти scout-ов:
- A: typecheck всех TS-пакетов (api, orchestrator, device-agent, web, packages/ai, db, queue, storage).
- B: все тесты (apps/orchestrator/test, apps/device-agent/test, packages/ai/test) + prisma validate.
- C: Python editor/video-processor/publisher: py_compile + `import app.main`.
- D: `pnpm audit --prod` + pip-audit (если есть) + health localhost:3000/3001 + инвентарь: список роутов API (метод+путь+есть ли auth) и список вызовов в apps/web/src/lib/api.ts — отметить расхождения.
Запиши сводку в BASELINE.md. Красный typecheck/тесты — сразу кандидаты в план (приоритет high).

## Фаза 2 — аудит (параллельно, Sonnet)
Для каждой выбранной области — `code-auditor` (mode: audit) и `security-auditor`. Бриф каждому: ключ области, точные пути, акценты из таблицы, релевантные факты baseline (ошибки typecheck, расхождения контрактов), напоминание вернуть ответ в своём формате. Для крупных областей (api, web, orchestrator) дели на 2–3 подобласти по директориям, чтобы агент читал код, а не скользил по верху.
Если health показал, что API и web подняты — параллельно запусти `e2e-tester` по всем сценариям. Если нет — отметь в отчёте «e2e: окружение не запущено» и предложи пользователю поднять его (`docker compose up -d` + `pnpm dev`) в конце; сам без разрешения не поднимай.

## Фаза 3 — триаж и план (ты сам, думай тщательно)
1. Собери все находки, дедуплицируй (одна причина — одна задача).
2. Проверь сам по коду каждую critical/high и всё с `confidence: low`, которое хочешь оставить. Ложные срабатывания — выкинь с пометкой.
3. Ранжируй по (влияние × вероятность) / стоимость. Порядок: безопасность critical/high → сломанная функциональность → потеря данных/зависание пайплайна → производительность → упрощение.
4. Сгруппируй в задачи. Каждая задача: id, ссылки на находки, исполнитель, разрешённые файлы, критерии приёмки, команда проверки, зависимости.
5. Назначение исполнителя:
   - `quick-fixer` — механика, 1 файл, ≤30 строк, решение уже принято тобой в брифе.
   - `implementer` — обычный фикс/оптимизация/фича в пределах одного сервиса или узкого контракта api↔web.
   - **ты сам** — сквозные изменения между сервисами, модель auth/тенантов, миграции с данными, семантика очередей и конкурентности, публикация/ферма где ошибка дорогая, задачи, где аудиторы противоречат друг другу, и любые `escalate` от исполнителей.
6. Улучшения и новые функции: из IMPROVEMENTS/HARDENING и своего видения продукта выбери 3–7 с лучшим отношением ценность/цена, опиши каждую (что, зачем, цена, риск). Без `--auto-features` спроси пользователя через AskUserQuestion (multiSelect), что делать.
7. Запиши FINDINGS.md (все проверенные находки) и PLAN.md (волны задач). При `--audit-only` — останови работу здесь и выдай краткое резюме и ссылки на файлы.

## Фаза 4 — исполнение волнами
- В одной волне параллельно идут только задачи с непересекающимися наборами файлов; пересекающиеся — последовательно в следующих волнах. Изоляцию worktree не используй (правки должны остаться в этой рабочей копии).
- Бриф исполнителю самодостаточный: проблема, сценарий воспроизведения, точные файлы:строки, выбранное тобой решение (или рамки решения), критерии приёмки, команда проверки. Не «на основе находок», а своими словами.
- `escalate` или `failed` → разберись сам: сделай задачу или переформулируй бриф. Не переотправляй тот же бриф.
- Субагенты не коммитят. Коммиты — только если пользователь попросит.

## Фаза 5 — верификация
1. `scout` — повторить baseline полностью; сравни с BASELINE.md (не должно стать хуже ни в одном пункте).
2. `code-auditor` mode `diff` по каждой изменённой области (параллельно); при задачах безопасности — ещё `security-auditor` по диффу.
3. Если окружение поднято — `e2e-tester` по затронутым сценариям.
4. Регрессии → новая волна исправлений. Максимум 2 круга; что осталось — в отчёт как открытое.

## Фаза 6 — отчёт
REPORT.md: что проверено, что исправлено (задача → файлы → как проверено), что добавлено, открытые проблемы с приоритетом, что не удалось проверить и почему (e2e, ферма, прод), рекомендации следующего шага. Пользователю — краткое резюме по-русски и ссылки на файлы.

## Жёсткие правила для всех
- Продакшен (k-m-m.online, боевой сервер, боевая БД) не трогать: ни запросов, ни деплоя, ни миграций.
- Не запускать реальную публикацию в соцсети и платные AI-API без явного разрешения пользователя.
- Ферма телефонов — на другом ПК: только статический анализ device-agent.
- Никаких деструктивных команд: `git reset --hard`, `git clean`, `stash`, force-push, `docker compose down -v`, `prisma migrate reset`, удаление данных.
- Секреты не печатать и не переносить в отчёты.
- Экономия: Haiku для механики, Sonnet для кода, Opus — для мышления. Брифы с точными путями, ответы субагентов — сжатые.
