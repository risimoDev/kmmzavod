## P0 — устранить в первую очередь

### P0-01. Повторная отправка уже начатой или завершённой публикации

`publish-now` выбирает элемент раздачи по статусу `scheduled`, затем без проверки текущего состояния возвращает связанный `PublishJob` в `scheduled`. Удаление предыдущей задачи происходит после изменений БД. Ошибка удаления игнорируется, а новая задача получает другой идентификатор. Если между выборкой и записью воркер начал отправку или публикация успела завершиться при отставшем статусе элемента, новый воркер может повторно захватить заявку. Watchdog проверяет `published` и `failed` по своему снимку, но для остальных строк тоже меняет БД до проверки состояния BullMQ. Атомарный захват в самом publish-воркере эту гонку не устраняет. Источники — `apps/api/src/routes/autopilot.routes.ts:696–755`, `apps/orchestrator/src/autopilot/loop.ts:688–777`, `apps/orchestrator/src/workers/publish.worker.ts:267–324`.

**Исправление.** Разрешить ручной и автоматический перенос только для однозначно ожидающих задач через условный переход состояния. Хранить устойчивый идентификатор операции и отдельное состояние `outcome_unknown` для случаев, когда внешняя сторона могла принять ролик. Сверять такие операции с результатом площадки до повторной отправки. Критерий — при одновременной работе `publish-now`, watchdog и воркера мок-провайдер получает один вызов, включая потерю ответа после принятия публикации.

### P0-02. Реквизиты прокси присутствуют в истории Git

Чтение версии `apps/device-agent/deep-diagnose.ps1` из `7c8e783` подтвердило наличие строки с логином и паролем в URL прокси. Текущий скрипт перенесён на переменные окружения. Доступность этих реквизитов у провайдера и охват распространения истории неизвестны. Источники — коммит `7c8e783`, `apps/device-agent/deep-diagnose.ps1`, `AUDIT_FIXES.md`.

**Исправление.** Отозвать старые реквизиты у провайдера, просмотреть журнал их использования и просканировать полную историю, артефакты и архивы. Решение об очистке общей Git-истории принимать после отзыва и согласования с владельцами клонов. Критерий — старые реквизиты отозваны, актуальные находятся в хранилище секретов, проверка новых коммитов выполняется автоматически.

## P1 — высокий приоритет

### P1-01. Внутренняя аутентификация ломает вызовы при включении

Compose передаёт `INTERNAL_SERVICE_TOKEN` в контейнеры. Python-сервисы проверяют `x-internal-token` при непустом значении. Клиенты оркестратора и прямые вызовы API этого заголовка не добавляют. При заданном токене перестанут работать соответствующие запросы редактора, обработки видео и опционального publisher. При пустом токене сервисы полагаются на доступ к Docker-сети. В редакторе внутренняя граница особенно важна, поскольку сервис умеет принимать локальные пути и скачивать URL с редиректами. Источники — `docker-compose.yml:118,186,231,268,320`, `apps/editor/app/main.py:23–35`, `apps/editor/app/services/storage.py:69–93`, `apps/video-processor/app/main.py:26–39`, `apps/publisher/app/main.py:21–34`, `apps/orchestrator/src/services/editor.ts:157,199`, `apps/orchestrator/src/services/publisher.ts:60,80`, `apps/orchestrator/src/workers/video-compose.worker.ts:119,326`, `apps/api/src/routes/admin/pipeline-test.routes.ts:438`.

**Исправление.** Ввести общую клиентскую настройку и заголовок для всех соответствующих вызовов, затем сделать токен обязательным для production. Ограничить источники медиа доверенным хранилищем и изолировать сетевой доступ обработчиков. Критерий — анализ, монтаж, уникализация и публикация работают с токеном, а запросы без авторизации отклоняются.

### P1-02. Device-agent допускает удалённое управление при пустом токене

Привязка по умолчанию к туннелю и отдельный loopback уменьшают поверхность доступа. Сетевой обработчик, однако, пропускает запросы без проверки при пустом `DEVICE_AGENT_TOKEN`, а конфигурация допускает явную привязку ко всем интерфейсам. Это даёт любому клиенту, который может связаться с таким экземпляром, доступ к операциям агента. Скрипт установки отдельного VPS-прокси также разрешает установку без ограничения IP, оставляя только пароль. Источники — `apps/device-agent/src/config.ts:14–27,52–63`, `apps/device-agent/src/index.ts:39–47,1411–1455`, `scripts/vps-setup-proxy.sh:26,62–69,99–102`.

**Исправление.** Завершать запуск сетевого агента при отсутствии токена. Ограничить туннель, входящие соединения и VPS-прокси списком разрешённых адресов. Проверить запуск при позднем появлении туннеля, доступ с локальной машины и отказ при отсутствии или неверном токене.

### P1-03. Next.js зафиксирован на уязвимой и неподдерживаемой ветке

В `apps/web/package.json` закреплён Next.js `14.2.18`. Версия находится в диапазоне CVE-2025-29927, а используемый App Router также попадает под опубликованное описание отказа в обслуживании для 14.x. Middleware проекта участвует в перенаправлении с защищённых страниц. API перепроверяет авторизацию своей логикой, поэтому доступ к данным через один лишь обход Next middleware по этому аудиту не установлен. Ветка 14.x находится вне LTS. Источники — `apps/web/package.json`, `apps/web/src/middleware.ts`, `apps/api/src/plugins/auth.plugin.ts`. [Бюллетень о middleware](https://github.com/vercel/next.js/security/advisories/GHSA-f82v-jwr5-mffw) · [Бюллетень об App Router](https://nextjs.org/blog/security-update-2025-12-11) · [Политика поддержки](https://nextjs.org/support-policy).

**Исправление.** Перевести веб на поддерживаемую ветку, обновить lock-файл, проверить вход, защищённые страницы, сборку и проксирование через Nginx.

### P1-04. При сбое между PostgreSQL и Redis задания теряются

В раздаче захват элемента, создание заявки, присвоение `publishJobId` и добавление в BullMQ выполняются отдельными действиями. После частичного сбоя повторный запуск видит элемент уже `scheduled` и пропускает захват. Похожий разрыв есть в ручной публикации, анализе/рендере редактора и постановке задач уникализации. В `publish-now` ошибка постановки игнорируется и счётчик «отправлено» растёт. При отсутствии `publishJobId` ручной путь подставляет ID элемента, для которого publish-воркер не находит строку `PublishJob`. В автоматическом восстановлении покрыта лишь ограниченная выборка просроченных элементов автопилота. Источники — `apps/orchestrator/src/workers/distribute.worker.ts:262–312`, `apps/api/src/routes/publish.routes.ts:335–341`, `apps/api/src/routes/editor.routes.ts:422–450,689–707`, `apps/api/src/routes/uniquify.routes.ts:524,737,894–928`, `apps/api/src/routes/autopilot.routes.ts:727–756`, `apps/orchestrator/src/autopilot/loop.ts:683–699`.

**Исправление.** Записывать доменные изменения и намерение поставить задачу в одной транзакции PostgreSQL. Доставлять намерения из transactional outbox с детерминированными идентификаторами и сверкой. Критерий — отключение Redis или остановка процесса между любыми двумя вызовами оставляет заявку в наблюдаемом состоянии и даёт ей восстановиться без дубля.

### P1-05. Статус публикации, счётчики и раздача расходятся после частичного сбоя

При завершении публикации состояние `PublishJob`, счётчик `SocialAccount`, состояние `DistributeItem` и агрегаты `DistributeJob` записываются отдельно. Если обновление агрегата падает после закрытия элемента, повторный вызов пропускает уже закрытый элемент и счётчик не восстанавливается. Ошибка обновления аккаунта логируется, а следующий вызов видит `published` и не делает это обновление. Если БД недоступна после принятия поста, воркер может завершить задачу в BullMQ с `uploading` в БД. Завершение всех элементов также может переписать `cancelled` у раздачи через безусловное обновление. Источники — `apps/orchestrator/src/workers/publish.worker.ts:116–211,308–324,834–852`.

**Исправление.** В общей транзакции фиксировать результат, статус элемента и счётчики с условными переходами. Добавить восстановление агрегатов по строкам и отдельную очередь сверки уже отправленной публикации. Критерий — сверка восстанавливает все проекции после искусственного отказа записи, а отменённая раздача сохраняет состояние отмены.

### P1-06. Планировщик теряет редкие расписания и сдвигает секунды

`nextCronDate` ищет совпадение только на семь суток вперёд и переносит секунды текущего тика. Для `0 12 1 * *` в UTC после 2 ноября функция вернула `null`, хотя ближайший запуск 1 декабря. Для `* * * * *` после `05:00:42Z` функция вернула `05:01:42Z` вместо `05:01:00Z`. Рассылки читаются только с `nextRunAt <= now`; запись с `null` перестаёт исполняться. Схемы кампаний и раздач проверяют длину текста cron/часового пояса. Цикл поиска также форматирует время для каждой минуты, до 10 080 итераций на расписание. Источники — `apps/orchestrator/src/workers/scheduler.worker.ts:42–96,426–442,601`, `apps/api/src/routes/distribute-schedules.routes.ts:16–33`, `apps/api/src/routes/campaigns.routes.ts:27–28`.

**Исправление.** Использовать общий парсер cron и валидатор часовых поясов на записи и исполнении. Проверить первое число месяца, границу минуты, переходы DST и пропущенные тики. Ошибку расписания сделать видимой пользователю.

### P1-07. Создаваемые `VideoSchedule` не исполняются

API создаёт активную сущность `VideoSchedule` с `nextRunAt = now`; поля `autoPublish`, площадки и аккаунты сохраняются. Обращения к `db.videoSchedule` присутствуют только в CRUD-маршрутах API. Цикл оркестратора обслуживает пресеты, раздачи, кампании и автопилоты. Пользователь получает успешный ответ, но это расписание генерацию не запускает. Источники — `apps/api/src/routes/schedules.routes.ts:67–110`, `apps/orchestrator/src/workers/scheduler.worker.ts:133–179,425,595`.

**Исправление.** Подключить `VideoSchedule` к планировщику или явно вывести маршрут из эксплуатации с миграцией существующих записей. Критерий — создание расписания и наступление срока дают ровно один ожидаемый запуск либо API явно сообщает, что режим больше недоступен.

### P1-08. SSE размещает JWT в логах и не применяет обычный отзыв доступа

При недоступности SSE-cookie браузер передаёт access JWT в URL. Обработчик при таком входе пишет `req.url` в warning, а правила маскирования API скрывают заголовок Authorization. SSE также использует отдельную проверку, не перечитывающую активность пользователя и организации. Выдаваемый SSE-cookie JWT содержит ту же структуру claims и подпись, что access JWT. Назначение токена обычный `authenticate` не различает. Источники — `apps/web/src/hooks/useVideoProgress.ts:110–117,166`, `apps/api/src/routes/videos.routes.ts:54–93`, `apps/api/src/routes/auth.routes.ts:187–199,207–223`, `apps/api/src/plugins/auth.plugin.ts:29–62`, `apps/api/src/app.ts:51`.

**Исправление.** Убрать резервный вход по URL, по возможности использовать same-origin HttpOnly cookie или потоковый `fetch` с заголовком. Ограничить SSE-токен отдельным назначением и проверять актуальность доступа. Проверить маскирование логов и поведение открытого потока после блокировки пользователя.

### P1-09. Автоматическая генерация и списания допускают перерасход

Ручное создание задания резервирует кредиты. Планировщик пресетов создаёт свои `Video` и `Job` напрямую. `chargeCredits` уменьшает баланс без условия наличия средств и пишет `balanceAfter` с отсечением отрицательного значения, скрывая фактический остаток в журнале. Некоторые стадии отдельно записывают генерацию, выполняют списание и увеличивают `Job.creditsUsed`. При повторе после частичного отказа бухгалтерский эффект зависит от места остановки. Источники — `apps/api/src/lib/video-job.ts:85–152`, `apps/orchestrator/src/workers/scheduler.worker.ts:192–245`, `apps/orchestrator/src/lib/credits.ts:21–43`, `apps/orchestrator/src/workers/gpt-script.worker.ts:558–577`.

**Исправление.** Применять единое правило бюджета к автоматическим и ручным платным сценариям, с явной политикой перерасхода. Завести уникальный ключ списания на логическую операцию и фиксировать расход и журнал в одной транзакции. Критерий — повтор стадии после сбоя не удваивает списание, а журнал совпадает с фактическим балансом.

### P1-10. Транскрибация блокирует единственный HTTP-воркер video-processor

Асинхронный `/transcribe` после загрузки файла синхронно выполняет FFmpeg, probe и Whisper. Контейнер стартует с одним Uvicorn worker. Пока операция удерживает event loop, соседние HTTP-запросы и healthcheck ждут. Видеопайплайн вызывает этот маршрут для субтитров, поэтому задержка затрагивает обычный сценарий. Источники — `apps/video-processor/app/api/transcribe.py:71–107`, `apps/video-processor/app/services/transcribe.py:42–63`, `apps/video-processor/Dockerfile:27–31`, `apps/orchestrator/src/workers/video-compose.worker.ts:119,147`.

**Исправление.** Вынести блокирующую работу в ограниченный пул или отдельные задачи. Сохранить управляемую конкуренцию по CPU/памяти и измерить отклик `/health` под транскрибацией. Проверить восстановление при прерванном FFmpeg и исчерпании таймаута.

### P1-11. Деплой откатывает код без согласованного отката данных

`--rollback` запускает `git reset --hard HEAD~1`, а схема БД остаётся на уже применённой версии. Деплой удаляет отслеживаемый `docker-compose.override.yml` и собирает образы из изменяемого checkout. На релизе с несовместимой миграцией приложение может перестать запускаться и после отката. Источники — `scripts/deploy.sh:100–105,124–157,189–226,241–255`, `scripts/server-setup.sh:332–334,661–726`.

**Исправление.** Деплоить образ по SHA, явно выбирать Compose-файл и фиксировать версию схемы для каждого релиза. Использовать совместимые поэтапные миграции и проверенный сценарий восстановления. Критерий — откат к конкретному предыдущему образу в staging с актуальной схемой и без изменений рабочей копии.

### P1-12. Уже запущенная генерация может перезаписать отмену

API отмечает `Job`/`Video` отменёнными, убирает задачу координатора по ID и освобождает резерв. Координатор проверяет отмену перед стартом. Последующие этапы, например `gpt-script` и `video-compose`, читают запись без статуса, а итоговые обновления выполняют только по ID. Если отмена пришла во время активной обработки, работа может продолжиться и вернуть в БД `scenes_ready` или `completed`. Источники — `apps/api/src/lib/video-job.ts:218–253`, `apps/orchestrator/src/pipeline/coordinator.ts:24–43`, `apps/orchestrator/src/workers/gpt-script.worker.ts:281–288,597`, `apps/orchestrator/src/workers/video-compose.worker.ts:37,497–515`.

**Исправление.** Проверять отмену перед внешними вызовами и постановкой последующих стадий, применять условные переходы при сохранении результатов и отдельно учитывать операции, принятые до отмены. Критерий — отмена во время рендера сохраняет `cancelled` после позднего ответа провайдера, новые этапы не стартуют, резерв возвращается один раз.

## P2 — надёжность и сопровождение

### P2-01. Суточный лимит публикаций расходится с окном пользователя

Планировщик сбрасывает `dailyPostCount` по UTC, автопилот считает окно в своей таймзоне, а воркер раздачи проверяет сохранённый счётчик. Один аккаунт может считаться доступным на этапе планирования и получить пропуск на этапе отправки. В Екатеринбурге полночь UTC наступает в 05:00. **Исправление:** хранить используемую для лимита дату/таймзону и резервировать слот на аккаунт атомарно. Покрыть смену суток и параллельные раздачи. Источники — `apps/orchestrator/src/workers/scheduler.worker.ts:159–172`, `apps/orchestrator/src/autopilot/loop.ts:474–541`, `apps/orchestrator/src/workers/distribute.worker.ts:161`.

### P2-02. API разрешает параллельно запустить рендер одного проекта

Маршрут проверяет наличие клипов, без условия пишет `rendering` и отправляет задачу без `jobId`. Имя BullMQ-задачи не служит её уникальным идентификатором. Повторный POST может продублировать рендер и побочные записи. Анализ проекта устроен схожим образом. **Исправление:** условный переход, ключ операции для конкретной версии монтажа и защита воркера от устаревшей задачи. Источники — `apps/api/src/routes/editor.routes.ts:422–450,689–707`, `apps/orchestrator/src/workers/editor-render.worker.ts:100–156`.

### P2-03. Конфиг редактора смешивает клиентские и служебные поля

API принимает произвольный `config`, удаляет `voiceoverKey`, проверяет префиксы ключей и принадлежность `workspaceProjectId`. Поле `autopilotBatchId` остаётся в клиентском конфиге, хотя воркеры используют его как признак автоматического режима и на его основе меняют видимость/привязку выходов. PATCH сливает конфиг после отдельного чтения, поэтому параллельные запросы могут потерять изменения. **Исправление:** явная схема клиентских полей, служебная связь из БД и контроль версии при записи. Источники — `apps/api/src/routes/editor.routes.ts:63–88,739–773`, `apps/orchestrator/src/workers/editor-analyze.worker.ts:164`, `apps/orchestrator/src/workers/editor-render.worker.ts:100–116`.

### P2-04. Сбой загрузки медиа оставляет временный файл

`resolve_source` создаёт временный файл до сетевого запроса. Удаление есть в ветке превышения лимита, а `finally` вызывающего кода знает только о путях, которые функция успешно вернула. Ошибка HTTP, обрыв потока или отмена операции могут оставить файл на диске. **Исправление:** удалять файл в `finally` загрузчика до передачи владения, включая отмену, и учитывать общий размер рабочего каталога. Источники — `apps/editor/app/services/storage.py:69–93`, `apps/editor/app/api/analyze.py:122–128`, `apps/editor/app/api/render.py:41–58,92–96`.

### P2-05. После удаления монтажного проекта могут остаться объекты MinIO

DELETE в редакторе удаляет `EditProject` и связанные строки через Prisma. Операции удаления объектов для этого маршрута нет. Для загруженных исходников и результатов это означает риск роста хранилища и сохранения файлов после удаления проекта. Некоторые источники могут иметь общие ссылки, поэтому очистке нужна информация о владельце и ссылках. **Исправление:** асинхронная уборка с учётом оставшихся ссылок, TTL временных объектов и сверка потерянных объектов. Источники — `apps/api/src/routes/editor.routes.ts:341–372,1202–1207`, `packages/db/prisma/schema.prisma:1445,1471`, `packages/storage/src/minio.ts:191–198`.

### P2-06. Redis одновременно хранит очередь, блокировки и прогресс

Redis имеет `maxmemory 512mb` и `noeviction`, поэтому при заполнении новые записи могут отклоняться. В Compose есть том Redis, конфигурация AOF явно не задана, а подтверждённого плана восстановления очереди в скриптах нет. Задачи со внешним эффектом зависят от возможности восстановить намерения и блокировки после сбоя. **Исправление:** определить параметры сохранения и целевые RPO/RTO, измерять размер, задержку очередей и ошибки записи, восстанавливать задания из устойчивого журнала. Источники — `docker-compose.yml:20–35`, `packages/queue/src/queues.ts:75–82`, `apps/orchestrator/src/workers/publish.worker.ts:214–228`.

### P2-07. Секреты в браузере и в базе защищены неравномерно

Access и refresh-токены доступны JavaScript в `localStorage`, access-токен также пишется в читаемую cookie. При открытой второй вкладке `refreshInFlight` действует только внутри одной вкладки, а API потребляет прежний refresh-токен отдельной операцией от записи нового. Прокси-URL, который может включать пароль, сохраняется строкой в `SocialAccount`; маскирование API уменьшает риск ответа, оставляя значение в БД и копиях. **Исправление:** HttpOnly-сессии с CSRF-защитой для браузера, транзакционная ротация, зашифрованный секрет прокси и хранение ссылки на него. Источники — `apps/web/src/lib/api.ts:12–38,93–123`, `apps/api/src/routes/auth.routes.ts:142–174`, `apps/api/src/routes/publish.routes.ts:267–302`, `apps/api/src/routes/account-farm.routes.ts:902–955`.

### P2-08. Права сервисов на MinIO шире необходимого

Для API, оркестратора и медиа-сервисов Compose по умолчанию подставляет корневые реквизиты MinIO. Одновременно `MINIO_TAG` по умолчанию остаётся `latest`. Сбой или компрометация одного контейнера увеличивает охват доступа к объектам, а повторная сборка стенда может дать другой образ. **Исправление:** отдельные сервисные учётные записи с правами на нужные операции/префиксы и закреплённый образ с процедурой обновления. Источники — `docker-compose.yml:37–46,85–86,152–153,262–263,308–309`.

### P2-09. Нет автоматических барьеров релиза и проверенного восстановления

В `.github` есть конфигурация агента, каталог workflow отсутствует. Корневой `package.json` не объединяет тесты, а `turbo.build.outputs` учитывает `dist/**`, хотя веб собирается в `.next`. Отсутствуют сквозные тесты Fastify/PostgreSQL/Redis, контрактные тесты Python-сервисов и проверяемый restore drill для PostgreSQL и MinIO. В Git отслеживаются 57 файлов кеша `.turbo`, `tsconfig.tsbuildinfo` и резервная версия скрипта. В корне два lock-файла, контейнеры используют pnpm. **Исправление:** один воспроизводимый прогон CI с frozen lock, миграциями, тестами отказов, сканированием и сборкой, плюс расписание резервирования и проверка восстановления на стенде. Исключить генерируемые файлы из отслеживания в отдельном изменении. Источники — `.github`, `package.json`, `turbo.json`, `package-lock.json`, `pnpm-lock.yaml`, `.gitignore`, `apps/web/Dockerfile:18–32`.

### P2-10. Ошибки производственного пути плохо видны по healthcheck

API `/health` проверяет доступность PostgreSQL и Redis. Эта проверка может оставаться зелёной при остановке обработки очереди, ошибке внутренней авторизации или недоступности медиа/фермы. Есть heartbeat оркестратора и диагностика сервисов, но для оператора важны возраст старейшей задачи, рост неподтверждённых публикаций, расхождения счётчиков и частота повторов. **Исправление:** вывести эти показатели, назначить пороги, добавить correlation ID через API, BullMQ и агента, связать алерты с инструкциями сверки. Источники — `apps/api/src/app.ts:154–183`, `apps/orchestrator/src/index.ts:426–439`, `apps/api/src/routes/admin.routes.ts:167,1156`, `scripts/check-health.sh:240–265`.

### P2-11. Веб-клиент делает тяжёлые запросы на крупных экранах

В диагностической сборке `/admin` требует около 240 кБ First Load JS, `/dashboard` — 217 кБ, `/farm` — 164 кБ. Страница автопилота агрегирует несколько наборов данных и подписывает медиа-ссылки на каждый запрос. Линтер отмечает 14 мест с обычными `<img>` и зависимость `selectedVariant` в эффекте страницы видео. Это измерения сборки и наблюдение по коду. Влияние на LCP и нагрузку БД требует профилирования. **Исправление:** начать с замеров, разделить быстрые статусы и тяжёлый журнал, затем оптимизировать загрузку изображений и проверить переключение варианта при обновлениях. Источники — `apps/api/src/routes/autopilot.routes.ts:395–550`, `apps/web/src/app/(app)/videos/[id]/page.tsx:125`, вывод `next build`.

## Что перепроверено после предыдущего аудита

- Redis healthcheck из R1 теперь получает `REDIS_PASSWORD` через окружение контейнера. Это подтверждено по конфигурации, а фактический запуск контейнера требует Docker Engine.
- R2/R3 для агента учтены в коде: IP туннеля вычисляется при повторе через getter, отдельный loopback существует. Проверка токена и запуск на реальном Windows-хосте остаются самостоятельными задачами. Источники — `docker-compose.yml:23–32`, `apps/device-agent/src/config.ts:52`, `apps/device-agent/src/index.ts:1416–1459`.
- Атомарные переходы в publish/distribute добавлены. Основные остаточные риски находятся в вызывающих маршрутах, записи итогов и разрывах между БД и очередью. См. P0-01, P1-04, P1-05.
- Тест SNI, который падал в прежнем отчёте, прошёл на текущих файлах. Тесты координат тоже прошли. Значение refresh-токена больше не дублируется в cookie. Старые прокси-реквизиты по-прежнему присутствуют в истории Git.
- В обычной авторизации роль берётся из БД и активность организации проверяется на запросе. Резерв ручной генерации и его возврат используют транзакции. Порты основной инфраструктуры в dev override и порты веб/API на хосте привязаны к loopback. Эти меры стоит сохранить при исправлениях. Источники — `apps/api/src/plugins/auth.plugin.ts`, `apps/api/src/lib/video-job.ts:85–105,175–205`, `docker-compose.override.yml:7–25`, `docker-compose.yml:62–65,341–343`.
