## C. Критические

### C1. device-agent открыт всей сети и не проверяет токен
- `apps/device-agent/src/index.ts:1392` — `const listenHost = '0.0.0.0'`, хотя комментарий в `config.ts:47` требует «never 0.0.0.0». В лог при этом пишется `config.HOST`, то есть лог врёт.
- `config.ts:60` объявляет `AGENT_TOKEN`, но в `src/` нет ни одного `addHook` — токен нигде не сверяется. Оркестратор и API его тоже не отправляют.
- Итог: любой, кто видит ПК фермы по сети, может без пароля ставить APK (`/device/apps/upload-and-install`), выполнять shell и JS на платах (`/device/scripts/run`), тапать, печатать, снимать скриншоты, менять прокси, логинить аккаунты.

**Как чинить**
1. Слушать только адрес туннеля: `app.listen({ host: config.HOST, port })`.
2. Сделать токен обязательным (падать при старте, если пуст) и добавить проверку:
   ```ts
   app.addHook('onRequest', async (req, reply) => {
     if (req.method === 'GET' && req.url === '/health') return;
     const got = Buffer.from(String(req.headers['x-agent-token'] ?? ''));
     const want = Buffer.from(config.AGENT_TOKEN);
     if (got.length !== want.length || !timingSafeEqual(got, want)) {
       return reply.code(401).send({ ok: false, error: 'Unauthorized' });
     }
   });
   ```
3. Добавить заголовок `x-agent-token` в `apps/orchestrator/src/services/device-agent.ts` и `apps/api/src/lib/device-agent.ts` (один axios-instance с `headers`).
4. Правило Windows Firewall: порт 8300 только с IP прод-сервера в туннеле.
5. `bodyLimit: 1 ГБ` (`index.ts:35`) оставить только для потокового роута APK; для JSON — 1–2 МБ. Ветку «APK в base64 внутри JSON» (`index.ts:1277`) убрать: она держит весь файл в памяти.

### C2. Ложный «Published» вернулся через восстановление из черновиков
`apps/device-agent/src/publish.ts:345-363` — `recoverAndPublishDraft` возвращает `ok: true, posted: 'yes'` **всегда**, если удалось нажать «Опубликовать»: и когда `verified.profile === false`, и когда цикл ожидания загрузки просто истёк по таймауту. Дальше `publish.ts:964` отдаёт это как успех, воркер ставит `published`. Это тот же класс бага, что «47 ложных постов» из раздела 11 документа.

Вторая проблема там же (`publish.ts:242-257`): берётся «первый черновик в списке» или тап в точку (25%, 35%) экрана. Если в черновиках лежат старые ролики (а они копятся — см. раздел 10 документа), опубликуется чужой ролик с подписью от текущего.

**Как чинить**
- Передавать в `recoverAndPublishDraft` `baseline` и считать успехом только `isNewPostOnProfile(baseline, after)`. Иначе возвращать `ok: false, posted: 'unknown', retryable: false`.
- Перед публикацией запоминать число черновиков; восстанавливать, только если их стало ровно на один больше. Иначе — не трогать и отдать человеку.
- Если на плате официальный TikTok с RU-блокировкой, восстановление бессмысленно (ролик снова уйдёт в черновики) и съедает ~7 минут на каждый пост. Ограничить: одна попытка, и отключать при повторном провале на той же плате.

### C3. Кнопка «Перезапустить все упавшие» может выложить ролик дважды
`apps/api/src/routes/autopilot.routes.ts:768-780`:
- В выборку попадают все `failed`, включая те, что упали с «публикация не подтверждена» (`posted: 'unknown'`). Воркер специально не ретраит их, потому что пост может уже висеть в профиле — а кнопка ретраит.
- Попадают `skipped` (дневной лимит, health < 30, непрогретый аккаунт). Publish-воркер эти лимиты повторно не проверяет — защита обходится.
- Попадают даже `published` с определённой пометкой: статус сбрасывается и пост уходит заново.
- Счётчики `DistributeJob.failedCount/publishedCount` не откатываются, после ретрая сумма превышает `totalItems`.

**Как чинить**
- Делить на три группы: «точно не опубликовано» (ретраить), «не подтверждено» (сначала `/stats/profile` и сверка, ретраить только если поста нет), «skipped» (ретраить только через distribute-воркер, чтобы лимиты сработали).
- При ретрае декрементировать `failedCount` и возвращать `DistributeJob.status` в `distributing`.
- В документе (раздел 12) убрать совет «жать большую красную кнопку» без проверки профиля.

### C4. `apply-vps-proxies.ps1` не работает: `$host` — зарезервированная переменная PowerShell
`apps/device-agent/apply-vps-proxies.ps1:57-83` — `$host = $null`, `$host = $matches[4]`. `$Host` в PowerShell — константа, присваивание даёт ошибку «Cannot overwrite variable Host because it is read-only or constant», а скрипт идёт дальше. В `host` каждой записи попадает объект консоли, а не IP. В агент уходит мусор.

Остальное в том же скрипте:
- `:118` `$parsedProxies[$i % $parsedProxies.Count]` — если прокси меньше, чем плат, несколько плат молча получают один IP.
- Порядок плат берётся из `adb devices` и не стабилен: при повторном запуске аккаунты получают другие IP.
- `:133-140` режим `private_parallel` включается **до** привязки прокси и с `inactivePolicy = "direct"`. Если `batch-set` упал, платы параллельно выходят напрямую с российского IP.
- В конце всегда печатается «НАСТРОЙКА ЗАВЕРШЕНА», даже при ошибках.

**Как чинить**
- Переименовать `$host/$port/$user/$pass/$type` → `$pHost/$pPort/...`; в начало скрипта `Set-StrictMode -Version Latest; $ErrorActionPreference = 'Stop'`.
- Формат файла сделать `SERIAL=IP:PORT:USER:PASS` — жёсткая привязка плата↔VPS. Если плат больше, чем прокси — выходить с ошибкой.
- Порядок: `batch-set` → `batch-check` (все IP не RU и все разные) → только потом `proxy/mode`. Политика — `block`, не `direct`.
- Итоговый код возврата и текст — по факту проверок.

### C5. `install-tiktok-mod.ps1` стирает сессии аккаунтов до установки
`apps/device-agent/install-tiktok-mod.ps1:78` — `pm clear com.zhiliaoapp.musically` выполняется первым делом на всех платах. Это не «очистка кэша» (как сказано в документе), а полное удаление данных: все аккаунты разлогинятся. Если APK затем не встанет (мод подписан другим ключом → `INSTALL_FAILED_UPDATE_INCOMPATIBLE`, нужен `uninstall`), плата остаётся без сессии и без мода.

Также:
- `:104` «[УСПЕХ] … НА ВСЕ ПЛАТЫ» печатается безусловно.
- `:81` ставятся **все** `*.apk` из папки `apks/` — туда же кладёт файлы `apk-manager`, поставится лишнее.
- APK из неофициальных сборок никак не проверяется; это код с полным доступом к аккаунтам.
- Документ говорит «устанавливает параллельно» — цикл последовательный.

**Как чинить**
- Сначала `adb install` на одной тестовой плате; `pm clear` — только после успешной установки и только по явному флагу `-WipeData`.
- При несовпадении подписи — явное сообщение и отдельный флаг `-Reinstall` (uninstall + install), потому что это потеря сессии.
- Имена файлов и SHA-256 задавать параметрами, сверять хеш перед установкой.
- Считать успехи/ошибки по платам, итог — по факту.
- Параллельность: `Start-Job`/`ForEach-Object -Parallel` или вызов `/device/apps/install` агента.

### C6. «Все 20 плат одновременно» невозможно: `publish.concurrency = 2`
`packages/queue/src/queues.ts:82`. Воркер публикации обрабатывает максимум 2 задачи сразу, значит в `private_parallel` одновременно работают 2 платы, а не 20. Кроме того `distribute.worker.ts:177` раздвигает посты на `itemIndex × staggerMinutes` (для автопилота минимум 3 мин, `loop.ts:542`) независимо от режима — 20 плат растянутся на час.

**Как чинить**
- `concurrency` ≥ числа плат (например 24). От двойной работы на одной плате уже защищает `lock:device:<id>`.
- В `shared_sequential` ожидание общего замка (до 150 с, `publish.worker.ts:446`) держит слот воркера. При большом `concurrency` это допустимо, но лучше сразу `moveToDelayed`, а не ждать в цикле.
- В distribute для `private_parallel` заменить линейный stagger на случайный разброс в пределах окна (например 0–10 мин).

## H. Высокий приоритет

### H1. Дубли BullMQ-задач на один `PublishJob` → ложный `failed`
- Distribute ставит задачу с `jobId = publishJob.id` (`distribute.worker.ts:293`).
- Watchdog (`loop.ts:716-721`) и retry-failed (`autopilot.routes.ts:838-850`) удаляют задачу по `publishJob.id`, но новую ставят с id `watchdog-…`/`retry-…`. При следующем проходе watchdog свою же задачу уже не найдёт и добавит ещё одну.
- Задача, которая честно ждёт занятую плату (перекладывается каждые 90 с), через 25 минут считается «застрявшей» — в `shared_sequential` с очередью из 20 плат это обычная ситуация.
- Когда две задачи одного `PublishJob` стартуют рядом, вторая видит `status = 'uploading'` (`publish.worker.ts:218`) и помечает публикацию как «прервана перезапуском» — пока первая реально публикует. Потом первая ставит `published`, но `DistributeItem` уже закрыт как `failed`, счётчики расходятся.

**Как чинить**
- Добавить в `PublishJob` поле `bullJobId`; единая функция `enqueuePublish(publishJobId, delay)` в `packages/queue`: удалить задачу по сохранённому id → добавить новую → сохранить id. Использовать её во всех трёх местах.
- Захват задачи сделать атомарным:
  ```ts
  const claimed = await db.publishJob.updateMany({
    where: { id: publishJobId, status: { in: ['pending', 'scheduled'] } },
    data: { status: 'uploading' },
  });
  if (claimed.count === 0) { /* published → выйти; uploading → проверить lock:device, не фейлить вслепую */ }
  ```
- «Упал посреди загрузки» определять по отсутствию `lock:device:<id>` и возрасту `updatedAt`, а не по одному статусу.
- Watchdog не должен трогать элементы, у которых задача жива в BullMQ (`getJob` → `isDelayed()/isWaiting()/isActive()`).

### H2. Watchdog обходит учёт и зацикливается на элементах без `publishJobId`
`apps/orchestrator/src/autopilot/loop.ts`:
- `:682-689` — статус `DistributeItem` правится напрямую, `publishedCount/failedCount` не растут → `DistributeJob` никогда не станет `completed`. Нужен вызов `settleDistributeItem`.
- `:693, :708` — если `publishJobId` пуст, в payload уходит id самого `DistributeItem`. Воркер пишет «PublishJob not found, skipping», элемент остаётся `scheduled`, и так каждые 25 минут. Нужно либо создать `PublishJob`, либо закрыть элемент как `failed`.

### H3. Аккаунт с низким health штрафуется за то, что он на паузе
`publish.worker.ts:269-274` бросает обычный `Error` для «disabled» и «health score too low». Это 3 бессмысленных ретрая, а на финале (`:817`) ещё −20 к `healthScore`, потому что текст не попадает в `INFRA_ERROR_RE`. Health растёт только на успешном посте (+5), а distribute пропускает всё, что ниже 30 — аккаунт заперт навсегда.

**Как чинить:** оба случая — `UnrecoverableError` и без штрафа; добавить в шедулер восстановление health со временем (например +5 в сутки без ошибок).

### H4. Отменённая раздача: элемент навсегда остаётся в `publishing`
`publish.worker.ts:239-242` безусловно ставит `DistributeItem.status = 'publishing'` (перезаписывая и `cancelled`), а проверка отмены идёт позже (`:301-307`) и просто делает `return` без `settleDistributeItem`. Элемент в `publishing` → в `distributeWindow` аккаунт вечно считается «прошлый пост ещё публикуется».

**Как чинить:** проверку отмены перенести до смены статусов; обновление элемента делать с фильтром `status: { in: ['pending','scheduled'] }`; при отмене вызывать `finalizePublishFailure`.

### H5. Пропущенные (`skipped`) элементы «сжигают» уникальные копии, а лимиты в двух местах разные
- Вариант считается свободным только при `distributeItems: { none: {} }` (`loop.ts:346, 484`). Если distribute пометил элемент `skipped`, копия больше никогда не будет выдана.
- Автопилот считает квоту как `min(число окон, group.maxPostsPerDay)` в таймзоне автопилота (`loop.ts:510`). Distribute считает по `dailyPostCount` с дефолтом **3** без группы (`distribute.worker.ts:161`), а сбрасывается счётчик по UTC (`scheduler.worker.ts:163`). При 4+ окнах в день или постах около полуночи по МСК автопилот назначает, distribute пропускает.
- Distribute требует 3 часа между постами аккаунта (`:97, :196`). Если окна автопилота ближе 3 часов, пост сдвигается и блокирует следующее окно.

**Как чинить**
- Фильтр свободных копий: `distributeItems: { none: { status: { notIn: ['skipped', 'cancelled'] } } }`.
- Одна функция `canPostNow(account, now)` в общем пакете, используемая и в `loop.ts`, и в `distribute.worker.ts`. Сутки считать в таймзоне группы/автопилота.
- При сохранении автопилота валидировать: интервал между окнами ≥ 3 ч + 2×jitter.

### H6. ИИ-советник может привести к двойной публикации
`apps/device-agent/src/publish.ts:777-816`. Если модель вернула `tap` по кнопке «Опубликовать», но не проставила `marks: 'share'`, флаг `shareTapped` не ставится, `posted` остаётся `'no'`. Дальше экран не распознаётся, флоу завершается с `retryable: true` — BullMQ повторяет и выкладывает ролик второй раз.

Рядом:
- `:210, :565, :760` — `new RegExp(aiDecision.targetText)` без экранирования (на `:780` экранирование есть). Скобка в ответе модели роняет шаг исключением.
- Ответ модели не валидируется: `action` вне списка, координаты за пределами экрана.
- Координаты: код считает нормализованными только значения ≤ 1, всё остальное — пиксели. Документ обещает шкалу 0–1000. Модели часто отвечают в координатах уменьшенной картинки → тап мимо.
- Текст с экрана (чужие подписи, комментарии) уходит в промпт — это канал для prompt injection.

**Как чинить**
- После любого ИИ-тапа: если нажатый элемент совпадает с `findPostButton(screen)` или экран был compose и перестал им быть — ставить `shareTapped = true; posted = 'unknown'`.
- Общий хелпер `escapeRegExp`; zod-схема для ответа; `clamp` координат в размеры экрана.
- В промпте жёстко: «координаты 0–1000 относительно картинки», в коде — всегда масштабировать.
- ИИ разрешить только закрытие диалогов и «Далее»; тап по «Опубликовать» оставить детерминированному `findPostButton`.

### H7. Таймаут оркестратора меньше худшего времени работы агента
Оркестратор ждёт `/publish` 20 минут (`services/device-agent.ts:102`). В агенте: ожидание мьютекса 2 мин + compose 3 мин + загрузка 8 мин + верификация до 3 × 8 мин + восстановление черновика ~7 мин. При превышении оркестратор пишет «не подтверждена» и отпускает замок, а агент продолжает публиковать.

**Как чинить:** общий дедлайн в `publishToDevice` (например 15 мин), от которого отсчитываются все внутренние циклы; таймаут оркестратора = дедлайн агента + запас.

### H8. Живой прогресс: один Redis-ключ на автопилот
`publish.worker.ts:176` пишет в `autopilot:live:<autopilotId>`, API читает его же (`autopilot.routes.ts:516`). В параллельном режиме платы затирают друг друга, в UI — случайная плата. Плюс каждая задача опрашивает агент раз в 1,5 с (`:518`) — 20 плат дают ~13 запросов/с через туннель.

**Как чинить:** `HSET autopilot:live:<id> <deviceId> <json>` + `EXPIRE`; API отдаёт массив. Опрос — один общий `GET /publish/progress` раз в 3–5 с на весь воркер.

### H9. `scripts/vps-setup-proxy.sh` — прокси открыт всему интернету
- `client pass { from: 0.0.0.0/0 }` и `ufw allow <port>/tcp` без ограничения источника.
- Пароль по умолчанию — `openssl rand -hex 6` (48 бит) при переборе из интернета.
- Пароль передаётся аргументом (`bash -s -- 1080 kmmuser ПАРОЛЬ`) — остаётся в history и виден в `ps`.
- Создаётся системный пользователь с паролем. Оболочка `/bin/false` не мешает SSH-туннелированию (`ssh -N -D`), если на VPS разрешён вход по паролю.
- `curl … | bash` из ветки `main` — любой коммит в репозиторий исполняется от root на 20 серверах.
- `command: bind connect udpassociate` — `bind` и UDP не нужны.
- `NET_IFACE=$(… | awk '{printf $5}')` — `$5` используется как формат printf, позиция поля зависит от вывода `ip route`.

**Как чинить**
- Четвёртый параметр — IP источника (NL-сервер): `client pass { from: $ALLOW_IP/32 … }`, `ufw allow from $ALLOW_IP to any port $PORT proto tcp`.
- Пароль: `openssl rand -base64 24`, читать из переменной окружения или stdin.
- В `sshd_config`: `DenyUsers kmmuser` (или `PasswordAuthentication no`).
- Ставить скрипт по конкретному тегу/хешу коммита и сверять SHA-256.
- `command: connect`; интерфейс: `ip -o -4 route get 8.8.8.8 | sed -n 's/.* dev \([^ ]*\).*/\1/p'`.

### H10. Маршрут «ферма → VPS» в документе не сходится с кодом
Раздел 9 сам объясняет, что голый SOCKS5 из РФ режется DPI. Но `apply-vps-proxies.ps1` отдаёт агенту публичные IP VPS, и агент подключается к ним напрямую с ПК фермы. Шаг 3 («проброс на прод-VPS или общая подсеть WireGuard») нигде не автоматизирован, скрипта нет.

**Как чинить (выбрать одно):** (а) на NL-сервере 20 DNAT-портов, в `vps-proxies.txt` писать `10.66.66.1:<порт>`; (б) добавить IP всех VPS в `AllowedIPs` туннеля на ПК фермы. В обоих случаях `inactivePolicy = block` и проверка в `preflight`, что страна выхода не RU. Проверять на ПК фермы, не на dev-ПК.

### H11. Повтор `POST /publish` на запасной адрес
`apps/orchestrator/src/services/device-agent.ts:60` — при `ETIMEDOUT` запрос повторяется на альтернативный IP туннеля. `ETIMEDOUT` бывает и после отправки запроса; для `/publish` это второй запуск публикации. Fallback оставить только для `ECONNREFUSED/EHOSTUNREACH/ENETUNREACH` либо только для GET.

### H12. Секреты и гигиена репозитория
- `apps/device-agent/vps-proxies.txt` (пароли 20 прокси) и `apps/device-agent/apks/` не в `.gitignore`.

- `.env.example` в `.gitignore` — шаблона переменных в репозитории нет, раздел 13 документа проверить не по чему.

- Скриншоты экранов аккаунтов уходят стороннему реселлеру `api.claudehub.fun` — осознанно оценить риск.
